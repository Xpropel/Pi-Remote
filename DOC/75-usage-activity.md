## 1. 功能说明：设置 › 使用活动

### 1.1 它是什么

设置页新增一个**一级页签「使用活动」**，用一张活动图展示你最近使用 pi 的频率：近一年每天的使用热力图（默认）、近 14 周周柱状图、或从有记录起的累计曲线；上方四张汇总卡（近 30 天），下方明细（最活跃的一天 / 单日 Token 峰值 / 平均每日消息）与按模型分布。设计参照 Codex 设置页的「Token 活动」热力图，视觉为 Pi-Remote 定版混搭风格（深色定版，见 §6）。

### 1.4 两组切换（互相独立，别合并）

| 组 | 选项 | 决定什么 | 默认 |
|---|---|---|---|
| **统计指标** | 消息数 / Token / 会话数 | 「数什么」：主图每格/每柱的数值、主图标题、汇总卡主指标联动 | **Token** |
| **查看方式** | 每天 / 每周 / 累计总量 | 「怎么看」：主图形态（热力图 / 周柱 / 累计面积） | **每天** |

两组正交：任意「指标 × 查看方式」组合都成立（如「消息数 × 每周」= 每周消息柱状图）。

### 1.5 主图三种形态

- **每天（默认）= 热力图**：近一年 **52 周 × 7 行**（行=周日→周六，52 列从今天所在周往回数；今天所在周之后不渲染数据），每格一天；格子颜色按**分位数**分档（长尾数据下线性分档会让图几乎全浅）；空格为浅底；「今天」的格子加**陶土橙描边环**；下方月份轴；右上图例「少 → 多」。悬停（窄屏点按）出白色亮面浮层：一行日期（如「10月22日 · 周四」）+ 一行三数值（Token · 消息 · 会话）；浮层避开最右两列、不压住今天格。
- **每周 = 柱状图**：近 **14 周**，每周一柱；峰值周标注数值；底部一行解读（最近一周区间 + 数值）。
- **累计总量 = 面积曲线**：从**有记录起**累计到今天，终点标注累计值；底部两行解读（累计起点/总量 + 「本月新增 vs 此前月份平均」对比；少数据走「数据积累中」）。
- 产品实现上**主图区只留一块**，切换「查看方式」时在原位换形态（不是三张图并排）。

### 1.6 汇总卡 ×4（前三张近 30 天；连续天数为全期）

| 卡 | 主数字 | 补充行 | 口径 |
|---|---|---|---|
| 近 30 天 Token 总量 | 如 12.6M | ↑38% 较前 30 天 | 近 30 天 `totalTokens` 合计（API 处理量，见 §3.1） |
| 发送消息数 | 如 3,214 条 | ↑12% 较前 30 天 | 只数用户发送的消息（`role=user`，见 §3.4） |
| 活跃天数 | 如 14 / 30 天 | 占近 30 天的比例；少数据时「数据积累中 · 已记录 N 天」 | **当天有任意活动**（有会话或有消息）即算活跃（见 §3.6） |
| 最长连续使用 | 如 9 天 | 当前已连续 6 天 | 按本地时区自然日的**全期**最长连续（当前连续跨到今天；见 §3.6） |

- 前 3 张卡的主数字为**近 30 天**口径；「最长连续使用」取**全期**最长（附当前连续天数）。
- 环比只在前一窗口有数据时显示；前 30 天无数据时补充行显示「数据积累中」（见 §5.2）。
- 数字格式：Token 用 K/M（如 86.4K / 12.6M），消息/会话用千分位整数。

### 1.7 明细与按模型分布

- **最活跃的一天**：日期 + 星期 + 当天**用户消息数**/会话数；口径 = 快照窗口内**单日 `role=user` 消息数最多**的一天（**不叠加 assistant 回复**，见 §3.6/附录 A）。
- **单日 Token 峰值**：数值 + 日期（快照窗口内单日 `totalTokens` 最大日）；**该数值用陶土橙**（全页仅「今天」格描边与这处数值用橙）。
- **平均每日消息**：按近 30 天的**活跃日**计算（不是按 30 天），注明口径。
- **按模型分布**：近 30 天按 Token 量横条占比；显示**前 4 名 + 「其他」**（模型超过 4 个时第 5 名起合并「其他」；聚合层最多保留 8 行）。

### 1.8 窄屏（≤420 宽）

- 左导航变**顶部横向滚动**条；汇总卡两列；热力图**横向滚动**，初始自动滚到**最近一端**（密集区与今天直接露出）；主图/明细/模型分布上下堆叠。
- **数据一个不少，只改排法**；无横向溢出的页面级滚动条。

## 2. 数据来源与隐私边界

### 2.1 唯一数据源：设备本机的 pi 会话文件

- 数据来自**运行 pi 的设备本机**的会话日志：`~/.pi/agent/sessions/--<项目路径>--/<时间戳>_<会话id>.jsonl`（一个会话一个文件，每行一个 JSON 条目）。
- 覆盖该设备上 pi 的**全部落盘会话**（包括没有经过 Pi-Remote 的本地会话）；新版 pi 的压缩/分支摘要不删除原始条目，不影响计数（见 §3.9）。
- relay 服务器上的 room 记录只是同一批数据经 Pi-Remote 同步过的**子集**，**不与本机文件混加**（否则会重复计数）。
- 不统计：没有落盘的会话（`--no-session`）、已被删除/移入废纸篓的会话（下次扫描即减少）。

### 2.2 数据链路（谁算什么）

```
设备本机：pi 会话 jsonl（~/.pi/agent/sessions）
   │  扩展扫描 + 增量缓存 <agentDir>/usage-days.json（只在本机）
   ▼
extension 聚合为 UsageSnapshotV1（每日 token/消息/会话、模型行、summary）
   │  usage_snapshot（只传聚合快照）
   ▼
relay：校验（形状/版本/上限/敏感键拒绝）→ 按「账号 + 设备」哈希落盘缓存
   │  viewer 用 usage_get 请求 → relay 回 usage_snapshot
   ▼
三套 UI 设置页「使用活动」渲染
```

- **聚合发生在设备端**（extension），不在 relay、不在浏览器。
- relay 只缓存聚合快照（`data/accounts/usage/<hash(account)>-<hash(device)>.json`，原子写），**不含任何会话内容**。
- 设备端缓存是 `<agentDir>/usage-days.json`（per-file 指纹 + 每日聚合贡献），也不含正文。
- 浏览器只收到聚合快照；三套 UI 共用同一份数据。

### 2.3 隐私边界（准确表述）

| 项 | 说明 |
|---|---|
| **哪些内容不出设备** | 原始会话内容/正文、会话标题、工作目录（cwd）、消息 id、工具调用内容、文件路径——**都不出设备**，也不进入快照 |
| **哪些计数会传输** | 仅**每日本地聚合计数**：tokens（总量/输入/输出/缓存）、消息数（用户/助手）、会话数、模型名与对应 token 合计、时间信息（本地时区、日期） |
| **relay 缓存什么** | 上述聚合快照（按账号 + 设备），无内容；relay 管理员可见聚合数字，但**不含任何对话内容** |
| **鉴权** | viewer 只能读取**本账号**设备的快照；请求其他账号/未知设备 → 统一空态（不区分错误，避免探测） |
| **强制校验** | relay/UI 校验层**拒绝**含 `cost`/`content`/`cwd`/`title`/`text`/`path` 等敏感键的快照（只允许聚合计数） |
| **金额** | **不读、不传、不展示**（`usage.cost` 实测不可信，见 §3.2） |
| **删除会话** | 删除/移入废纸篓后，下次聚合不再计入 → 数字会相应变小（符合「现存文件」口径） |

### 2.4 多设备

- v1 快照按**设备独立**；设置页展示**当前设备**的使用活动（设备来自设备名册/当前选择）。
- 跨设备合并统计为后续能力（当前不提供，见 §8）。

### 2.5 隐私表述规范

- 对外表述请**只使用 §2.3 的写法**，不要自行简化成更强的隐私承诺（例如「数据不经过服务器」这类说法是不准确的）。
- 准确说法：**原始会话内容不出设备；只上传本机聚合计数，由 relay 按账号+设备缓存并展示；缓存与传输不含正文/标题/cwd**。

## 3. 数字口径（最重要的阅读章节）

> 这一章解释页面上每个数字「怎么算、为什么这样、别怎么理解」。遇到「数字和我感觉不一样」先看这里。

### 3.1 Token 活动 = API 处理量（不是用户的打字量）

- **怎么算**：把每条 assistant 消息自带的 `usage.totalTokens` 按天求和（`totalTokens = input + output + cacheRead + cacheWrite`，pi 已算好）。
- **为什么数字会很大**：pi 每轮对话都会把**完整上下文重新提交给模型**——系统提示、工具声明、前面所有轮次都在里面。实测只问一句「hi」，这一轮的 input 就有约 1530 token。所以长会话里同一批内容会被**重复计入**多次。
- **这个口径能用来做什么**：画「哪天用得多 / 用得少」完全成立（Codex 的 Token 活动也是同一口径），也是业界常见做法。
- **不能怎么写**：不能把它解释成用户的打字量/生成内容量（例如「输入字数」「产出内容量」这类说法都不准确）。用户真正打的字连零头都不到。
- 页面文案统一使用「**Token 活动 / Token 用量**」，不出现把用量描述成用户打字量的表述。

### 3.2 不显示金额

- pi 的 assistant 消息里有 `usage.cost` 字段，但**实测不可靠**：有的 provider 没配价格表时整段为 0，不同来源的同字段也可能出现非 0 值。
- 因此本项目**不读取、不传输、不展示任何金额/费用**；不使用金额做计费依据。
- 页面上只有 token/条数/天数类指标，没有人民币/美元等金额展示。

### 3.3 分天按「本地时区」

- 所有「每天」都按**设备本地时区**的自然日切分（不是 UTC，也不是服务器时区）。
- 原因：UTC 切天会让晚上使用的量记到第二天，整张热力图会错位一天。
- 设备时区/夏令时变化后，聚合缓存会作废并按新时区重新扫描（用户无需操作）。
- 跨时区旅行时，同一天的历史可能按新时区重算（属正常现象，口径仍一致）。

### 3.4 消息计数：只数「用户发送」的消息

- 每日「消息数」= `role == "user"` 的消息条数。
- **排除**：`system`（新版 pi 每个会话首条是系统提示）、`toolResult`（工具回执）、`custom`、`branchSummary`/`compactionSummary` 等非用户角色。
- 手机端经 Pi-Remote 发送的消息，在 pi 本体里同样落成 user 消息，不会漏计。
- assistant 回复数在快照里另有记录（含失败轮），当前页面主指标使用「用户消息数」。

### 3.5 会话数与历史起算

- **一个 jsonl 文件 = 一个会话**；会话按文件 header 的开始时间落到对应本地日。`/fork`、`/clone` 出来的会话是新文件，各自单独计。
- **历史起算** = 该设备上**现存最早的会话文件**那一天（不是安装 Pi-Remote 的日期）。
- **上限 400 天**：超过一年多的历史会被截断（保留最近 400 天），快照带「已截断」标记；热力图一年视图不受影响。
- 被删除/移入废纸篓的会话：下次聚合不再计入，数字会变小（这是正确行为，不是 bug）。

### 3.6 活跃天数、连续天数、峰值与平均

| 指标 | 口径 |
|---|---|
| 活跃天数 | **当天有任意活动**（当天有会话开始、或有用户消息、或有 assistant 回复）即算活跃；与连续天数使用同一谓词 |
| 最长连续使用 | 按本地自然日计算的最长连续活跃天数（**全期**；谓词同上，只有消息没有新会话的日子也算） |
| 当前连续 | 以「最近有数据的一天/今天」为基准算到今天；今天没数据则为 0（不会因为「还没开始用」报警） |
| 单日 Token 峰值 | **快照窗口内**（最多 400 天）单日 `totalTokens` 最高的一天（日期 + 数值） |
| 消息峰值（最活跃的一天） | **单日 `role=user` 消息数最多**的一天（**不叠加 assistant 回复**；对齐设计「最活跃的一天」与真值账本） |
| 平均每日消息 | 近 30 天用户消息总数 ÷ **有消息的活跃日数**（不是 ÷30，页面会注明） |

> **窗口口径要分清**：汇总卡四张的主数字是**近 30 天**（以设备本地「今天」为锚）；`summary.totals` 即近 30 天合计；环比由 UI 用前 30 天数据自算。连续天数（streaks）是**全期**口径；单日峰值取**快照窗口内**最大值；模型分布是**近 30 天**。

### 3.7 按模型分布

- 按每条 assistant 消息的 `provider/model` 分组，把 token 求和；展示近 **30 天**的占比。
- 聚合层最多保留 **8** 行；页面显示**前 4 名 + 「其他」**（第 5 名起合并进「其他」）。
- 虚拟模型/路由场景下，assistant 记录的是**实际应答的物理模型**，正是这里想要的分布。

### 3.8 时间窗口与三种查看方式

| 位置 | 窗口 |
|---|---|
| 汇总卡 4 张 | 近 30 天（环比对比「前 30 天」） |
| 热力图（每天） | 近一年（52 周 × 7 行，最多 366 天；上限 400 天留余量） |
| 周柱状图（每周） | 近 14 周 |
| 累计面积（累计总量） | 从有记录的第一天累计到今天 |

### 3.9 删除、压缩（compaction）与废弃分支的影响

- **compaction（上下文压缩）**：只在喂给模型时压缩上下文，**不删除**会话文件里的原始条目——所以压缩过的老会话，历史计数不变（这是好消息）。
- **树形分支**：一个会话文件里可能有被放弃的分支（`parentId` 树），v1 统计文件中**全部**消息行（精度影响可忽略，文档如实注明；不做分支树回溯）。
- **失败轮**：`stopReason` 为 error/aborted 的 assistant 回复也算一条回复（可单列），v1 计入 assistant 计数。
- **顶层 usage 条目**（如缓存预热、compaction 摘要那一次调用）：v1 **不计入**每日 token（口径以 assistant 消息为准，避免与其他地方口径不一致）。

### 3.10 不提供/算不准的指标（如实说明）

| 指标 | 状态 | 原因 |
|---|---|---|
| 金额/费用 | ❌ 不提供 | `cost` 字段不可信（§3.2） |
| 使用时长 | ❌ 不提供 | 只有首末消息时间差，含挂机/离开，不是真实使用时长 |
| 时段分布（几点最活跃） | ❌ 当前不提供 | 数据可算，但本期页面不做（后续可扩展） |
| 输入字数/打字量 | ❌ 不提供 | 无按键/字数统计；用文本长度估算会误导 |
| 阅读量/界面停留 | ❌ 不提供 | pi 与 relay 都不记录任何 UI 曝光/停留数据 |
| 工具调用次数 | ⏸ 可算但当前未展示 | 数据存在（toolCall/toolResult），后续可加 |

## 4. 页面数据与刷新

### 4.1 页面只消费快照，不自己聚合

- 三套 UI 的设置页共用同一个「使用活动」页面组件（`UsageActivityPage`）；页面**只消费聚合快照**（`UsageSnapshotV1`），不在浏览器里扫描/聚合任何本地文件。
- 页面通过 `useUsageActivity(relay, { deviceId })` 取真实数据（`ui/src/pi/usage/useUsage.ts`）；设置页把 `relay` 与当前设备 `deviceId` 传入。**dev 预览/测试**才用 `snapshot` prop 注入演示快照（不进生产数据路径）。
- 页面数据依赖「当前设备」：设置页从设备名册取当前设备，向 relay 请求**该设备**的快照（v1 按设备独立，见 §2.4）。
- 切换 UI 变体（Cursor/Claude/Codex）不会重新聚合、不会重新请求；同一份快照三套 UI 复用。

### 4.2 首次打开页面的时序

```
打开 设置 › 使用活动
  ├─ UI 先看握手 caps：没有 usage.activity.v1（旧 relay）→ 直接 unsupported 空态，不发请求
  ├─ 未认证 → 等待认证（不报错）
  └─ 发 usage_get{ deviceId, requestId, force? }
       ├─ relay 有新鲜缓存（≤5 分钟）→ 回 usage_snapshot（设备离线/名册无设备时 stale=true）
       ├─ 需要刷新 → relay 向设备发 usage_refresh{deviceId, requestId}
       │    └─ 设备端扩展增量扫描（正常毫秒~百毫秒；首次全量可能数秒）
       │         └─ usage_snapshot（extension→relay）→ relay 校验/缓存 → 回给页面
       └─ 等待超时 8 秒 → 回缓存（stale=true）或空态（timeout）
  └─ UI 收到后再用共享 validateUsageSnapshot 校验一次（防旧 relay/坏数据），通过才渲染
```

- 页面收到帧后记录更新时间（`receivedAt` 或快照生成时间），可供「数据统计于 HH:mm」类展示使用。
- 同一设备的并发请求会合并为一次设备刷新（relay 侧 pending 合并），多个页面/窗口拿到同一快照；超时 8 秒，**不无限转圈**。
- 数据量参考：本机 30 个会话文件 / 33.7MB / 1.5 万行，全量扫描约百毫秒级（纯读+解析）；历史增长后靠增量缓存，只重扫新增/修改的会话文件。

### 4.3 刷新方式

| 方式 | 行为 |
|---|---|
| 打开/重新进入页面 | 自动请求；relay 缓存新鲜（5 分钟内）时秒开 |
| 空态/错误态的「重试」 | 调用 `refresh()`（`force: true`），跳过 relay 缓存、请求设备重新聚合；保留已加载数据时不清空页面 |
| 新会话之后 | 重新进入/重试即可看到当天数字变化（v1 不做实时推送） |

> 页面级常驻刷新按钮不是必需；当前实现主要在空态/错误态提供「重试」。协议已支持 `force` 刷新，供后续 UI 扩展。

### 4.4 缓存与「数据可能不是最新」

- relay 缓存新鲜期 **5 分钟**（`USAGE_CACHE_TTL_MS`）；同一设备 5 分钟内的重复打开直接返回缓存。
- 以下情况会返回**已有缓存但标 `stale:true`**（页面提示「数据可能不是最新」）：设备离线、设备不在 relay 名册（如 relay 重启后）、刷新超时。
- 设备离线且**没有缓存** → 空态 `device_offline`；relay 重启且无缓存 → 空态 `no_data`。
- 缓存只是聚合数字，不包含任何会话内容（见 §2.3）。

### 4.5 数字格式与展示规则

| 规则 | 说明 |
|---|---|
| Token 缩写 | <1000 原样；≥1000 用 K（1 位小数，去尾 0）；≥1e6 用 M（如 86.4K / 12.6M） |
| 条数/天数 | 千分位整数（如 3,214 条 / 24 天） |
| 环比 | 仅前一窗口（前 30 天）有数据时显示 ↑/↓ 百分比；否则「数据积累中」；持平显示「—」 |
| 百分比 | 取整显示（38%） |
| 热力图分档 | 按**分位数**分 5 档（长尾下线性分档会让图几乎全浅）；空格为最浅档 |
| 悬停浮层 | 一行日期（含星期）+ 一行三数值（Token · 消息 · 会话） |

### 4.6 体验与性能

- 热力图一年最多约 366 格，一次渲染无压力；400 天是上限（超出截断）。
- 拉取/计算期间不阻塞设置页其它分区；加载中显示轻量占位（骨架/保持上次内容），不白屏。
- 三套 UI、深浅主题、窄屏布局共享同一页面组件，只有外壳/导航不同。

## 5. 空态、少数据与降级

> 本章对应「页面为什么是空的/旧的/数字不动」类问题。所有降级都**不报错、不白屏**。

### 5.1 空态：全新用户（还没有任何会话）

- **前提**：数据源可用（设备端支持使用活动能力），只是这台设备上还没有会话记录。
- 四张汇总卡显示 0；热力图全为浅格；页面一行说明：**「开始和 pi 对话后，这里会出现你的使用活动」**。
- 不出现错误提示、不留空白区、不影响设置页其它分区。
- **与「不支持/禁用说明」的区别**：空态 = 有数据源但 0 会话；不支持 = 设备/版本能力缺失，页面显示说明卡（见 §5.3 前两行）。两者文案不可混。

### 5.2 少数据：有会话但不足 30 天

- 汇总卡环比行改为**「数据积累中」**（不显示 ↑/↓ 百分比，避免「↑∞%」这类误导）。
- 累计面积曲线照常从第一天画起；热力图有几天数据亮几天。
- 活跃天数卡的补充行显示「数据积累中 · 已记录 N 天」；「平均每日消息」按已有活跃日计算。

### 5.3 降级矩阵（用户可见行为）

| 场景 | 页面行为 | 说明 |
|---|---|---|
| 旧 relay（握手 caps 无 `usage.activity.v1`） | 页面显示**说明卡**：「当前连接版本不支持使用活动」+ 指向本文档 §7 | UI 直接判定 unsupported，不发无用请求；不崩溃 |
| 设备端扩展旧（无 cap） | 页面显示**说明卡**（入口仍可进）：「当前设备版本不支持使用活动，升级设备端后可用」+ 指向本文档 §7 | relay 发 `usage_refresh` 得 `unknown_type` → 回 `unsupported`（不重试）；若有旧缓存则先显示缓存 stale |
| 设备离线 | 有缓存：显示上次数据并提示「**设备离线，展示上次缓存**」；无缓存：说明卡「**设备离线，暂无可展示数据**」 | 对应 `stale:true` / `device_offline` |
| relay 重启后设备不在名册 | 有缓存：显示缓存 + stale；无缓存：空态 | 对应 `no_data` |
| 无数据（设备在线、0 会话） | 正常空态：「开始和 pi 对话后，这里会出现你的使用活动」 | 有数据源但 0 数据，与「不支持」不同 |
| 请求了非本账号/未知设备 | 统一空态（不区分原因） | 防探测 |
| 扫描超时（>8s） | 有缓存显示缓存（stale）；无缓存空态/超时提示 | 下次打开/刷新会重试 |
| 部分文件读不了/坏行 | 页面正常，跳过坏文件/坏行 | 覆盖率信息不打扰用户 |
| 快照坏/超限/含敏感键 | relay 丢弃并记日志；等待的页面到 8 秒超时回缓存 stale 或空态 | 不转发坏数据 |
| 快照版本不认识（未来 v2） | 空态「数据版本不兼容」 | 只处理认识的版本，避免错误渲染 |
| 多设备 | 只显示**当前设备** | v1 不合并跨设备 |

> 空态（有数据源但 0 会话）与「不支持/禁用说明」（能力缺失/版本旧）是两种状态，文案不可混（§5.1）。

### 5.4 页面脚注（口径声明）

页面底部口径小字（当前实现文案）：

> 统计仅在本机聚合；经 relay 传输与缓存的只有每日聚合计数（tokens / 消息 / 会话 / 模型名），不含对话内容；金额不统计。Token 为 API 处理量（每轮会重报上下文）；时间按设备本地时区自然日切分，仅统计现存会话。

要求：保持「本机聚合 + 只传聚合计数 + 不含内容 + 不展示金额」四要点，不要写成更强的隐私承诺（见 §2.5）。

### 5.5 什么时候会刷新

- 打开「使用活动」页时自动请求（relay 缓存 5 分钟内直接返回，不触发设备重扫）。
- 手动刷新（若页面提供刷新/下拉）会跳过缓存、请求设备重新聚合（数据量大时需要几秒级）。
- 新增对话后刷新即可看到当天数字变化；不刷新时可能看到 5 分钟内的缓存值。

## 7. 协议接入：`usage.activity.v1`

> 本章面向要接入/自建 relay 或设备端的开发者。唯一事实源：`protocol/v4.json`（能力位与 limits）、`protocol/usage-activity.md`（协议说明）、`ui/src/pi/usage/types.ts`（共享类型）；relay 实现见 `relay/usage.js`，设备端实现见 `extension/pi-remote-sync.ts`（usage 段）。
> `usage` 是**内置数据能力**（不是 DOC/74 的 40 个「可接入 provider 的 UI 扩展能力」之一，见 §7.9），但依赖协议版本与设备端能力位。

### 7.1 能力位、上限与实现常量

- **能力位**：`usage.activity.v1`，三处登记：extension 的 `CLIENT_CAPS`、relay 的 `RELAY_CAPS`、协议 `protocol/v4.json` 的 `caps`（由 `node protocol/sync.cjs` 生成 relay/extension 副本）。
- **快照版本**：`v = "usage.activity.v1"`（`USAGE_ACTIVITY_VERSION`）。
- **快照 `summary` 口径**：`totals` = 近 30 天（含今天，更早不计入）；`streaks` = 全期最长 + 当前连续；`peaks.tokens` = 快照窗口内单日 `totalTokens` 峰；**`peaks.messages` = 单日 `role=user` 消息数峰（不叠加 assistant）**；`models` = 近 30 天按 token ≤8。
- **协议 limits**（`protocol/v4.json`；改后跑 sync 与测试）：

| limit | 值 | 含义 |
|---|---|---|
| `usageDaysMax` | 400 | 快照最多保留天数（超出截断最旧并标 `coverage.truncated`） |
| `usageModelsMax` | 8 | 快照模型行上限（页面显示前 4 + 「其他」） |
| `usageSnapshotMaxBytes` | 262144（256KB） | 单快照字节上限；典型数据远小于此（≤64KB 级），超限由 relay 拒收 |
| `usageRequestTimeoutMs` | 8000 | relay 等设备刷新的超时 |

- **relay 行为常量**（非协议 limit）：缓存新鲜期 **5 分钟**（`USAGE_CACHE_TTL_MS`）；缓存版本 `USAGE_CACHE_VERSION=1`；
  relay 缓存文件 `data/accounts/usage/<hash(account)>-<hash(device)>.json`（按账号+设备哈希，原子写、模式 0600）；
  设备端缓存 `<agentDir>/usage-days.json`。

### 7.2 帧（三类，四方向）

| 方向 | 帧 | 字段（摘要） |
|---|---|---|
| viewer → relay | `usage_get` | `{ type, deviceId, requestId, force? }`；`requestId` 由 viewer 生成，回帧原样带回；`force=true` 跳过 relay 缓存（刷新） |
| relay → extension | `usage_refresh` | `{ type, deviceId, requestId }`；`requestId` 由 **relay** 生成，用于丢弃迟到/不符的应答 |
| extension → relay | `usage_snapshot` | `{ type, deviceId, requestId?, snapshot }`；快照为 `UsageSnapshotV1` |
| relay → viewer | `usage_snapshot` | `{ type, deviceId, requestId?, available, reason?, snapshot?, receivedAt?, stale? }`；`available:false` 时 `snapshot` 为空 |

- `reason` 枚举：`no_data | device_offline | unsupported | timeout | stale`；`stale` 在协议枚举中保留，但实现上「缓存可用」用 `available:true + stale:true` 表达（`reason:"stale"` 仅兜底）。
- 同一设备的并发请求合并为一次设备刷新；所有等待 viewer 收到同一快照。

### 7.3 relay 行为（按实现）

1. **鉴权与隔离**：viewer 只能读取本账号设备；未知/越权 `deviceId` → `no_data` 空态（不区分原因，防探测）；缓存按 `accountId + deviceId` 哈希隔离，不跨账号；relay 重启后缓存仍在。
2. **缓存优先**：`!force && 缓存 receivedAt ≤ 5min` → 直接回缓存；此时若设备离线/不在名册 → `stale:true`，否则 `stale:false`。
3. **设备不在名册**（relay 重启后/设备已删除）：有缓存 → 缓存 + `stale:true`；无缓存 → `no_data`。
4. **设备离线**：有缓存 → 缓存 + stale；无缓存 → `device_offline`。
5. **设备在线但无 `usage.activity.v1` cap**（旧 extension）：有缓存 → 缓存 + stale；无缓存 → `unsupported`。
6. **需要刷新**：向设备发 `usage_refresh`（同一设备 pending 合并），8 秒超时 → 最近缓存 + `stale:true`，无缓存 → `timeout`。
7. **校验**：收到设备快照先 `validateUsageSnapshot`（版本/形状/上限/敏感键）；失败丢弃并记日志（不转发坏数据）；`requestId` 不符视为迟到丢弃。
8. **不存内容**：relay 只缓存聚合快照；不存路径/正文/标题；缓存读写异常只记日志，不影响 relay 主流程。

### 7.4 设备端（extension）行为

- 只读 `PI_CODING_AGENT_DIR`（缺省 `~/.pi/agent`）+ `/sessions` 下的会话 jsonl；不修改 pi 存储、不改 relay 既有格式。
- 扫描上限：最多 **5000** 个文件；单文件 > **256MB** 跳过（计入 `coverage.skippedFiles`）；遍历超限置 `coverage.truncated`。
- 增量聚合：缓存 `<agentDir>/usage-days.json`（per-file `mtimeMs+size` 指纹 + 每日贡献 + 模型贡献）；命中缓存的会话文件不重扫；时区/缓存版本不符或缓存损坏 → 全量重扫。
- 只在对 `usage_refresh` 的响应函数里扫描（**不主动推送**）；刷新请求串行执行（避免并发扫描），不阻塞 pi 事件循环（逐行解析、坏行跳过计入 `coverage.errors`）。
- 只发送聚合快照；扫描出错回空快照 + `errors` 计数（永不抛出、不发内容/错误细节、不泄露路径）。

### 7.5 旧端兼容矩阵（按实现）

| 组合 | 行为 |
|---|---|
| 旧 relay（握手 caps 无 `usage.activity.v1`） | 新 UI `useUsageActivity` 握手后直接 `unsupported` 空态（**不发无用请求**）；不崩溃 |
| 旧 extension（无 cap） | relay 发 `usage_refresh` → 旧端回 `unknown_type` → relay 回 `unsupported`（有缓存先回 stale），不重试 |
| 旧 viewer | 不会发 `usage_get`；新 relay 不向未声明 cap 的 viewer 主动发任何 usage 帧，既有面不受影响 |
| 旧 extension + 新 relay（设备离线等） | 按 §7.3 的缓存/空态路径降级 |
| 坏/超限/含 cost 的快照 | relay 丢弃并记日志；等待的 viewer 到超时回缓存 stale / `timeout` 空态 |

### 7.6 降级原因码与用户文案（映射）

| reason / 标志 | 用户看到 |
|---|---|
| `no_data` | 「还没有可用的使用数据」空态（未知设备/越权/relay 重启无缓存同此） |
| `device_offline` | 「设备未连接，暂时无法获取使用活动」（有缓存则显示缓存 + 「数据可能不是最新」） |
| `unsupported` | 「当前设备/连接版本不支持使用活动」+ 升级说明 |
| `timeout` | 「获取数据超时」+ 可重试；有缓存先显示缓存 |
| `stale:true`（帧标志） | 正常数据 + 「数据可能不是最新」提示 |
| 数据源正常但 0 会话 | 空态「开始和 pi 对话后，这里会出现你的使用活动」 |

- relay 缓存版本不符/文件损坏按无缓存处理（重新向设备取）。

### 7.8 自建/第三方接入注意

1. 设备端：声明 `usage.activity.v1` cap；按 §7.2 回 `usage_snapshot`；发送前本地过一遍校验（版本/形状/上限/无敏感键）。
2. **只发聚合计数**：不得夹带正文/标题/cwd/消息 id/文件路径；不得读取或传输 `cost`；分天按设备本地时区。
3. relay：viewer 账号隔离 + 缓存 + 校验 + 旧端降级；只缓存快照，不缓存内容；缓存可落盘（重启可用）。
4. 不要混用 relay `data/rooms/*.jsonl`（同一批数据的子集，混加会重复计数）。

### 7.9 与 DOC/74 能力体系的关系（Lead 裁决口径）

- `usage` 属**内置数据能力**，**不登记**为 `@/pi/extensions` 的 40 个可接入 provider 能力之一；DOC/74 §4 不新增能力卡片，能力计数保持 40 不变。
- 页面降级说明**不**指向 DOC/74 的 `#cap-*` 锚点，而是指向本文档（§5.3/§7.5）。
- 它仍然依赖 **relay/设备端版本**（能力位 `usage.activity.v1`）：旧端不支持时按 §7.5 降级，但这属于版本兼容，不是「provider 接入」。

### 7.10 HTTP 接口

- **v1 不提供** HTTP 接口（如 `/api/usage`）——所有读取走 viewer 的 WS 帧（复用现有鉴权与连接生命周期）。
- HTTP/导出接口属可选后置能力，**暂未提供/预留**；请勿依赖或自行假设其存在。

## 8. 已知限制

1. **只有当前设备**：v1 按设备独立，不做跨设备合并；想看另一台设备的使用活动需切到该设备。
2. **不是实时**：没有推送；打开页面/手动刷新时拉取（relay 缓存 5 分钟），新数据可能延迟出现。
3. **历史上限 400 天**：更早的历史被截断（热力图一年视图不受影响）。
4. **废弃分支计入**：树形会话里被放弃分支的消息也计入（精度影响可忽略，未做分支树回溯）。
5. **顶层 usage 不计**：缓存预热/压缩摘要等 `type:"usage"` 条目不计入每日 token（口径以 assistant 消息为准）。
6. **旧版本限制**：旧 relay/旧设备端无能力位时页面不可用（说明卡）；需升级对应端。
7. **首次扫描成本**：历史很大时首次全量聚合可能需要数秒（超时 8 秒会降级为缓存/空态）；之后靠增量缓存。
8. **时区变化会重算**：跨时区后历史按新时区重新分天（口径一致，数字可能与之前看的不同）。
9. **不显示金额/使用时长/输入字数**：原因见 §3.2/§3.10；不要用其它来源数字自行折算展示。
10. **只统计该设备上落盘的 pi 会话**：没有落盘的会话、已删除的会话不计；relay 侧子集不作为数据源。

## 9. 常见问题（FAQ）与排错

**Q1：Token 数字为什么这么大？我只打了几句话。**
A：这是 **API 处理量**口径：每轮都会把完整上下文（系统提示、工具声明、历史）重新提交，长会话里同一批内容被重复计入——问一句「hi」也可能有 ~1500 input。它适合看「哪天用得多」，不代表你的打字量（§3.1）。

**Q2：为什么没有金额/费用？**
A：pi 的 `cost` 字段不可信（有的 provider 全 0、不同来源不一致），本项目不读不传不展示金额（§3.2）。

**Q3：为什么某一天是空白？**
A：那天没有会话落盘（或文件被删）；空白格=0，不是错误。另外请确认设备时区正确（§3.3）。

**Q4：为什么数字比之前少了？**
A：删除了会话或移入废纸篓后，下次聚合不再计入（§3.5/§2.3）；compaction 不会减少计数（§3.9）。

**Q5：为什么在手机上看到的和电脑不一样？**
A：同一份快照、不同布局（§1.8）；如果不同设备，各自统计各自的数据（v1 不合并，§2.4）。

**Q6：为什么页面说「当前版本不支持使用活动」？**
A：relay 或设备端扩展版本旧了（无 `usage.activity.v1` 能力位）。升级 relay 与设备端后可用；旧端不会崩溃（§5.3/§7.5）。

**Q7：数据多久更新一次？**
A：打开页面时拉取（relay 缓存 5 分钟）；手动刷新可强制重扫（§4.3）。无实时推送。

**Q8：我的对话内容会被上传吗？**
A：原始会话内容/标题/cwd 不出设备；只有每日聚合计数（token/消息/会话/模型名）经 relay 传输并按账号+设备缓存用于展示，relay 侧不含内容（§2.3）。

**Q9：为什么模型分布只有 4 项？**
A：页面显示前 4 名 + 「其他」；聚合层最多保留 8 行，避免长尾模型挤爆列表（§3.7）。

**Q10：为什么「平均每日消息」和我自己算的不一样？**
A：它按**近 30 天的活跃日**平均，不是除以 30（§3.6）。

**Q11：企业/自建部署需要额外配置吗？**
A：需要 relay 与设备端扩展都是支持 `usage.activity.v1` 的版本；数据在设备端聚合，relay 只透传/缓存（§7.3/§7.4）。

**Q12：能不能导出/通过 HTTP API 拿数据？**
A：v1 不提供 HTTP 接口（暂未提供/预留）；如需导出请后续版本再评估（§7.10）。

### 9.1 排错速查

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 页面一直加载/骨架 | 首次扫描慢（历史大）、relay 等待设备 | 等待 8s 超时后降级；再刷新重试（§4.2） |
| 页面空但设备有会话 | 设备端版本旧/未声明 cap | 升级设备端扩展；看 relay 日志 `unsupported`（§7.5） |
| 数字比终端/其它工具大很多 | 口径不同（API 处理量） | 正常，见 §3.1 |
| 某天/某时段数据明显偏 | 时区设置不对 | 检查设备时区（§3.3） |
| 刷新后仍不变 | relay 缓存 5 分钟/走缓存 | 手动强制刷新（§4.3） |
| 切到旧 relay 页面报错 | 旧 relay 不支持 | 升级 relay；旧端应显示说明卡不崩溃（§7.5） |

## 附录 A：快照速查（`UsageSnapshotV1`）

**顶层字段**

| 字段 | 类型 | 说明 |
|---|---|---|
| `v` | `"usage.activity.v1"` | 快照版本 |
| `generatedAt` | number(ms) | 生成时刻 |
| `deviceId` | string? | 设备 id（可选） |
| `timezone` | `{ id, offsetMinutes }` | 设备本地时区（IANA 名 + 偏移分钟） |
| `range` | `{ firstDay, lastDay, days }` | 覆盖范围；无数据时为 null |
| `days` | `UsageDay[]` | 每日聚合，升序、无重复、≤400 |
| `summary` | `UsageSummary` | 汇总/连续/峰值/模型 |
| `coverage` | `UsageCoverage` | 覆盖率/诊断（不展示主数据） |
| `cache` | `{ hit, generatedFrom }` | 聚合缓存信息（诊断） |

**每日（`UsageDay`）**：`date`（YYYY-MM-DD 本地日）、`tokens{total,input,output,cacheRead,cacheWrite}`、`messages{user,assistant}`、`sessions`。

**汇总（`summary`）**：`totals{tokens,messagesUser,messagesAssistant,sessions,activeDays}`、`streaks{current,longest}`、`peaks{tokens,messages|null}`、`models[{provider,model,tokens}]`（≤8，近 30 天）、`modelsWindowDays: 30`。

> **窗口口径**：`totals` = 近 30 天（以设备本地「今天」为锚、**含今天**；更早历史不计入 totals）；`streaks.longest` 全期、`streaks.current` 以最近数据日/今天为基准；`peaks.tokens` = 快照窗口内（≤400 天）单日 `totalTokens` 峰值、`peaks.messages` = 单日 **user 消息数**峰值（不叠加 assistant）；`models` = 近 30 天按 token 降序 ≤8。环比不在快照里，由 UI 用 `days` 前 30 天自算。
