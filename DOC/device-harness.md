# 多设备与远程打开 PI

> 本文说明设备与连接窗口的设计，以及为什么不把 pi 放到服务器上跑。协议契约以 `protocol/` 与 `readyUI/data-interface.md` 为准，实现细节见 `DOC/10-relay-backend.md`、`DOC/20-local-device.md`。

私人使用：一台云上的 relay，多台自己的电脑（Windows、Mac）连上来。网页和手机先选设备，再看这台设备上的会话；**设备正在"连接窗口"内时**，网页可以打开 PI、启用本机未活动的会话、或在指定目录里新建会话。

## 1. 现状

今天没有「设备」这个对象。

| 现在有的 | 实际是什么 |
|---|---|
| 房间 `room` | 一个 pi 会话。`id` 来自本机的 `sessionId` |
| 左侧列表 | 全部房间混在一起，按项目目录 `cwd` 分组 |
| 文案 | 桌面、手机、对照页都写「本机会话」 |
| 在线 | 这个会话的 pi 扩展还连着 relay。电脑开着但 pi 没开，服务器看不到它 |
| 扩展 | 跑在 pi 进程里面，**会主动连 `7001`**。pi 退出，连接一起断 |
| 启动方式 | 人在那台电脑上执行 `deploy\start-pi.cmd`（Mac 上尚无对应脚本） |
| `PI_REMOTE_LABEL` | 会话标题的兜底显示名，不是设备编号 |

命令已经会送到登记该会话的那条本机连接上。两台电脑如果同时开着 pi，会话能同时出现，但列表分不出是哪一台，两个同名目录会叠在一起。

relay 不跑 pi，也不保存模型密钥。云服务器只做转发和清单索引。对话正文留在各台电脑上，服务器只留账户、设备和对话文件清单（§11）。

## 2. 目标

1. 每台电脑有稳定身份和显示名。网页左侧先选设备，再选这台设备上的会话。
2. 两台都开着时，网页或手机可以分别控制，互不影响。
3. **设备不常连服务器**：只有人在电脑上执行"连接命令"（例如离开办公位之前）的那段时间，设备才在线。窗口内网页可以：看这台设备有哪些对话、哪些在活动、启用没有在活动的会话、在指定目录新建 pi 会话。pi 在那台电脑上启动，不在云上启动。
4. 打开之后，现有的镜像、发消息、发命令、增量同步都沿用，不重做协议。

不设注册/登录。本期账户固定 `admin`（`.env` 里 `PI_REMOTE_ACCOUNT` 缺省即此值），网页不展示账户。能打开网页的人就是持有 viewer token 的本人。

## 3. 三个状态

```
设备未连接（默认）          设备已连接（窗口期）            会话可控制
没执行连接命令          →   人在电脑上执行了连接命令   →   活动会话镜像 + 未活动可启用 + 可新建
服务器看不到它              服务器看到在线、可操作          能看、能发消息、能发命令
```

| 状态 | 判定 | 网页上 |
|---|---|---|
| 设备未连接 | 没有连接窗口（命令没在跑） | 设备在列表里（名册来自索引 §11），灰色。不能做任何操作；可看它**上次留下的会话清单** |
| 设备已连接 | 连接命令正在跑 | 可点击。活动会话在线可镜像；未活动会话可"启用"；可在 `projects` 里"新建" |
| 会话在线 / 离线 | 窗口内该 pi 进程的扩展还连着 | 在线=可看可发；未活动=在清单里，点"启用"让设备把它拉起来 |

「电脑开着」不等于「设备已连接」。服务器接触不到没执行连接命令的电脑。

> **存储模型**：服务器只存「账户→设备→会话清单」索引，不存对话正文；离线会话"可看清单、不可看历史"，打开一个未活动会话 = 让设备用该会话文件起一份 pi。概念草图见 §11。

## 4. 总体结构

```
网页 / 手机
    │  7002  viewer（和现在一样）
    ▼
云上 relay
    │  7001  只接受本机主动连入
    ├──────────────────────┬─────────────────────────┐
    ▼                      ▼                         ▼
 Windows 连接命令        Mac 连接命令              各台电脑上的 pi
 （离开前执行；          （同理；跨平台           （连接窗口内，扩展才连 7001；
   前台命令，退出即断）    同一个 node 脚本）          窗口外不连）
    │ 登记设备 + 启动/恢复 pi                        │ 每个活动会话一条连接
    └───────────────────────────────────────────────┘
```

两条连接，不要合成一条：

- **连接窗口（连接命令）**：代表设备。窗口内负责「我在线」和「请启动/恢复 pi」。前台命令，退出（Ctrl+C / 关终端 / 到点）即断。
- **pi 扩展**：代表会话。**只有连接窗口开着时才连 relay**（靠本机状态文件门控，§6）。pi 可以有多个，每个会话一条连接；pi 退出连接断，但窗口还在、设备仍在线。

上图里的 Mac 是概念上的第二台设备；本期执行只做 Windows 连接命令。

都从电脑主动连到 `7001`，沿用现有的 localToken。云上不反向连入家里或办公室。

## 5. 设备身份

每台电脑在自己的 `.env` 里写死，不由网页临时分配：

```
PI_REMOTE_ACCOUNT=admin
PI_REMOTE_DEVICE_ID=<首次生成后永不改的编号>
PI_REMOTE_DEVICE_NAME=Windows
PI_REMOTE_PROJECTS=D:\pi-myself;D:\work\app
```

| 字段 | 规则 |
|---|---|
| `accountId` | 本期固定 `admin`（`PI_REMOTE_ACCOUNT` 缺省即此值） |
| `deviceId` | 本机生成一次，写入 `.env`。重装系统才换。不用主机名 |
| `name` | 给人看的名字，如 Windows、Mac。可改，编号不改 |
| `platform` | 本期连接命令填 `windows`；`mac` 留给后续 |
| `projects` | 允许启动/新建 pi 的目录列表。网页只能从这个列表里选 |

`PI_REMOTE_LABEL` 继续只当会话标题的兜底，不再兼作设备名。

名册持久化：**每次执行连接命令时** `device_register` upsert 进 `data/accounts/admin/devices.jsonl`（§11）。窗口结束不删行；在线与否只留在内存里，文件只记名册和 `lastAttachAt`。进程重启后仍显示该设备未连接。
同一 `deviceId` 的新窗口顶掉旧窗口（重复执行命令/进程重启）。不要顶掉这台设备上的 pi 扩展连接。

## 6. 连接命令（取代常驻进程；本期核心新增）

**不做开机自启的常驻进程。** 设备默认不在线；只有人执行命令的那段时间在线。这同时消掉旧设计的三个坑：Windows 计划任务在 Session 0 弹不出用户桌面窗口、launch agent 要单独维护、以及"电脑开着就等于对网络暴露"。

命令形态（同一个 node 脚本 `deploy/attach.cjs`；本期包 Windows 壳 `attach.cmd`，`attach.sh` 后续再补）：

```
pi-remote attach [项目目录...] [--max-hours 12]
```

它做五件事：

1. **登记设备**：连上 `7001` 发 `device_register`（`accountId`/`deviceId`/`name`/`projects` 来自本机 `.env`，`platform` 由连接命令填写）。
2. **开门**：写本机连接状态文件（`~/.pi/agent/remote-attach.json`，内容含 deviceId 与到期时间）。**pi 扩展只有看到这个文件才连 relay**；命令退出即删。扩展用 `fs.watch` 盯它，文件出现立刻重连（不用等退避），文件消失立刻断开。
3. **接收启动请求**：窗口内响应网页的 `harness_start`——在 `projects` 白名单目录里新起一份 pi，或用指定 `sessionId` 的会话文件起一份 pi。拉起方式与现在的 `start-pi.cmd` 相同（新控制台 + 工作目录），所以扩展、`.env`、终端行为都不变。
4. **显示状态**：终端里实时打印——设备已连接、当前活动会话（= 窗口内已登记的房间，按 cwd 分组）、viewer 地址、已连接时长/剩余时间。
5. **退出即断**：Ctrl+C / 关终端 / `--max-hours` 到点 → 状态文件删除、设备登记断开 → 扩展断开、设备转「未连接」。本机已开着的 pi 进程**不受影响**，只是镜像断了。

「判定设备端是否有 pi 进程在活动」的答案 = **窗口内有哪些扩展登记了房间**（relay 侧 `rooms.online` 即权威，回给网页显示"在线"）；本机进程扫描只作为终端里的展示增强，不作为权威。

不使用 `pi --mode rpc` 把 pi 藏成没有窗口的子进程：本机终端仍是本体，网页仍是镜像。（将来若要无人值守，预留 `--headless` 参数，本期不做。）

连接命令不读取模型密钥、不转发会话内容——它只管设备身份与进程拉起；会话数据始终走扩展自己的连接。

## 7. 窗口内的远程操作（新建会话 / 启用未活动会话）

网页只对「已连接」设备开放操作；未连接时按钮禁用，提示「在电脑上执行连接命令」。

```
网页操作（带 deviceId）
        │
        ▼
relay 转给这台设备的连接窗口
        │
        ├─ 新建：harness_start{deviceId, cwd}
        │      ├─ 该 cwd 已有在线会话 → already_running，附 roomId（relay 可预判，不必转本机）
        │      └─ 没有 → 本机新控制台起一份 pi → 扩展登记 → 房间上线
        │
        └─ 启用：harness_start{deviceId, sessionId}
               用该 session 文件起一份 pi → 扩展登记 → 房间上线（= 打开一个未活动会话）
```

约束：`cwd` 必须在 `PI_REMOTE_PROJECTS` 里；`sessionId` 必须出现在该设备的会话清单里（§11）。网页不提供自由输入。启动请求在连接命令侧同一时刻只处理一个，忙则拒绝、不排队（防并发双开）。`started` 只代表"本机已拉起"，**会话上线以 `room_list` 出现新房间为准**——网页需要"启动中…"中间态与总超时（§8）。

两台设备可以同时各开各的。请求带 `deviceId`，relay 只转给对应的窗口连接。

## 8. 协议上要加的内容

现有会话帧（`snapshot`、`room_event`）不改；`command` 只加设备级寻址和 `harness_start`。

```jsonc
// 扩展 room_register 多带账户/设备字段（旧扩展不带 deviceId → 归「未登记设备」）
{ "type": "room_register", "room": { "id": "<sessionId>", "label": "…", "cwd": "…",
  "accountId": "admin", "deviceId": "<设备编号>", "deviceName": "Windows", "platform": "windows" } }

// 连接命令登记设备（窗口开始；不占房间）
{ "type": "device_register", "accountId": "admin", "device": { "id": "<设备编号>",
  "name": "Windows", "platform": "windows", "projects": ["D:\\pi-myself"] } }
```

窗口内远程操作不是新帧，而是现有 `command`：命令名 `harness_start`，`args` 里 `cwd` 与 `sessionId` 二选一；应答走现有 `ack`。线格式以 `DOC/50-protocol-delta.md` 为准。

- `status`：`started`（本机已拉起，会话未必上线）/ `already_running`（该 cwd 已有在线会话，`roomId` 即它）。
- 失败 `ok:false`，同时给错误码和可读文案：设备未连接 / 目录不在允许列表 / 会话不在清单 / 本机启动失败。
- **`harness_start` 不自动重发**（重发=起两份）。relay 只等「已拉起」**10s**；会话上线由 `room_list` 驱动，前端另有 **60s** 观察窗。
- 设备级命令寻址：`command` 帧增加可选 `deviceId`（替代 `room`）。`harness_start` 由 relay 转到该设备的**连接窗口**，设备在线即可发起，用来启用或新建会话。其余白名单命令转到该设备当前活动会话的连接；没有活动会话 → `device_no_active_session`。白名单：`switch_session` / `new_session` / `fork` / `clone` / `get_state` / `get_sessions` / `harness_start`。`prompt`/`steer` 永远走房间（镜像语义）。
- 错误码枚举（补进契约，前端做分支）：`no_device` / `device_offline`（= 没执行连接命令）/ `device_no_active_session` / `session_not_found` / `cwd_not_allowed` / `spawn_failed`；`manifest_stale` 只记日志。
- `device_detach` 帧预留，本期不实现，网页不提供「断开此设备」（见 §10 与 D6）：语义仍是只断窗口、不断本机 pi。
- 观众侧 `room_list` 增加 `devices[]`（`online`=窗口在跑）与房间的 `accountId/deviceId`。稳态下 `session_manifest` 仅在窗口内上报（步 0 仍沿用常连，见 §12）；帧以 `DOC/50-protocol-delta.md` 为准。

## 9. 网页

桌面、手机、对照页共用同一套设备和会话选择。

左侧从上到下：

1. **设备**：每台一行：名字、平台、已连接/未连接。未连接=灰，展示它上次留下的会话清单（索引，标注"未连接"）。
2. **已连接设备**才有操作区：「新建会话」（从 `projects` 选目录）与「启用未活动会话」（从清单选）。
3. **会话列表**：活动会话在上（在线，可订阅可发消息）；下面按 cwd 分组展示未活动会话（点"启用"= 让设备拉起）。
4. 空状态写「这台设备没有会话」；未连接设备的提示写「在电脑上执行连接命令后可操作」，不再写「本机 pi 已断开」。

选中未连接设备时可看清单但打不开；输入框禁用。手机页把设备选择放在会话列表上方，不另做一套数据。

## 10. 不做的事

- 不把 pi 或模型调用搬到云服务器。
- 不用远程 bash 去启动 pi。bash 仍由 `PI_REMOTE_ALLOW_BASH` 关闭，与本功能无关。
- **不做开机自启、不做常驻进程**：连接窗口必须是人在场时主动触发的——这是安全模型的一部分（下线的定义就是"没人在跑命令"）。
- 不从网页删除会话、不从网页关机、不从网页重启别人的设备。（「断开此设备」本期不做，`device_detach` 仅预留，见 D6。）
- 不做第二套用户账号。设备不靠网页「邀请码」注册，靠这台电脑自己的 `.env`。
- 不把连接窗口和 pi 扩展并成一条连接。pi 一关，只是这个会话离线；窗口还在，设备仍在线。

## 11. 服务器只保留清单

对话正文留在设备自己的会话文件里。服务器不为每段对话保存一份 jsonl。本期只有账户 `admin`。

```
data/accounts/index.jsonl                    # 这个 relay 上出现过的账户
data/accounts/<账户>/devices.jsonl           # 该账户用过的设备
data/accounts/<账户>/sessions/<设备>.jsonl   # 该设备上的对话清单
```

| 文件 | 一行是什么 |
|---|---|
| `index.jsonl` | 账户：编号、第一次出现、最后一次出现 |
| `devices.jsonl` | 设备：编号、名字、平台、允许打开的目录、最后一次连接（`lastAttachAt`） |
| `sessions/<设备>.jsonl` | 对话：会话 id、标题、目录、设备上的文件路径、消息条数、更新时间、是否活动 |

同一 id 只保留最后一行。**窗口内**清单实时更新；**窗口外**保留上次内容（陈旧但有信息量：最近在忙什么）。正在观看的会话仍在 relay 内存里转发，观众断开或进程重启后内存副本丢掉；要看正文，设备得处于连接窗口内，由本机 pi 把镜像送上来。

`data/rooms/*.jsonl` 是旧的正文存储。正式进程默认不再写入（`PI_REMOTE_PERSIST_TRANSCRIPTS=1` 才恢复）。已有文件仍按原来的保留期清理。

## 12. 落地顺序

> 阶段划分以 `DOC/71-protocol-v4.md` 为准。连接命令取代了原「常驻进程」步骤。

0. **索引层**：清单落盘、扩展 `session_manifest`（这一步沿用现有常连，不带窗口门控）、`get_sessions`，以及 `room_register` 带上账户/设备字段。不依赖连接命令。设备字段缺省归「未登记设备」。
1. **连接窗口**：`deploy/attach.cjs`（登记、状态文件、窗口门控、按 `cwd` / `sessionId` 拉起），以及 `harness_start` 路由和设备级命令寻址。
2. **网页先选设备**：未连接设备的只读清单不依赖连接命令；「启用」「新建」依赖步 1。
3. **收尾**：启动中间态与超时，以及 `harness_start` 的串行和 `already_running` 预判。依赖步 1。

## 13. 决策（已在 00 号文档落定）

下表以 `DOC/71-protocol-v4.md` §8 为准，不再待拍板。

| # | 决策 | 落定 |
|---|---|---|
| D1 | `accountId` 来源 | `.env` 的 `PI_REMOTE_ACCOUNT`，缺省即 `admin`；本期固定此值 |
| D2 | 是否默认停写对话正文（`PI_REMOTE_PERSIST_TRANSCRIPTS`） | 默认停；这是整个成本收益的来源 |
| D3 | 设备级命令白名单边界 | 白名单含 `harness_start`（§8）；发消息类永远走房间 |

| D5 | 窗口是否自动到期（`--max-hours` 默认值） | 默认 12h 自动断；Ctrl+C 随时手动断 |
| D6 | 网页是否可主动「断开此设备」 | 本期不做；`device_detach` 预留，只断窗口不断本机 pi |
